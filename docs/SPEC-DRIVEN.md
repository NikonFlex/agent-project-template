# Разработка от спецификаций: входящие → спеки → дельты

Инструкция для Claude Code. На неё ссылается `CLAUDE.md`:
«Требования берутся из specs/, а не из docs/incoming/».

## Суть

Требования приходят от людей в виде документов: ТЗ, переписка, заметки, макеты,
расшифровки созвонов. Они противоречат друг другу, устаревают и пишутся в разных
жанрах. Поэтому в проекте три места:

| Каталог | Что там | Правило |
|---|---|---|
| `docs/incoming/` | присланные документы как получены | не правятся; это **не требования** |
| `specs/` | замысел системы, файл на домен | единственный источник требований; меняется дельтой |
| `docs/journal/` | почему выбрали так | только дописывается |

Код пишется **только по `specs/`**. Нашёл требование только во входящем
документе — это не требование, а повод обновить спеку (или спросить владельца).

## С чего начать в новом проекте

1. Спросить у владельца продукта (см. «Вопросы владельцу», блок «Старт»), кто он
   и какие документы есть.
2. Создать каталоги и файлы:
   ```
   docs/incoming/index.yaml
   docs/incoming/README.md
   specs/README.md
   specs/glossary.md
   docs/journal/JOURNAL.md
   ```
3. Добавить `.rgignore` с одной строкой `docs/incoming/` — чтобы обычный поиск
   по коду не подсовывал входящие документы как требования. Искать там явно:
   `rg --no-ignore ... docs/incoming/`.
4. Сложить присланные документы в `docs/incoming/` и записать каждый в индекс.
5. Прочитать все входящие, выделить домены, написать первые спеки (шаг
   «Дистилляция» ниже).
6. Показать владельцу список открытых вопросов одним пакетом.
7. Только после этого — задачи и код.

## Конвейер

```
документ пришёл → снимок в incoming + запись в индекс
               → разбор: что нового относительно спек
               → дельта в спеке (или вопрос в «Открыто»)
               → статус в индексе: distilled / rejected / superseded
               → задача со ссылкой на пункт спеки → код → проверка по критерию из спеки
```

### 1. Приём документа

- Файл кладётся в `docs/incoming/` **как получен**, в Markdown (Google Doc,
  PDF, DOCX — конвертировать в `.md`, текст не менять).
- Файл больше не правится никогда. Пришла новая редакция — новый файл, старая
  запись получает статус `superseded`.
- Запись в `docs/incoming/index.yaml`:

```yaml
- path: docs/incoming/ТЗ на личный кабинет v2.md
  received: '2026-09-28'
  source: письмо от заказчика
  status: incoming          # incoming → reviewed → distilled | rejected | superseded
  sha256: <sha256sum файла>
  distilled_into:           # заполняется на шаге 3
  - specs/accounts.md
```

Статусы:

| Статус | Значит |
|---|---|
| `incoming` | положен, не читан |
| `reviewed` | прочитан, разобран, но в спеки перенесено не всё |
| `distilled` | всё нужное перенесено; `distilled_into` называет спеки |
| `rejected` | не берём; причина — в журнале |
| `superseded` | заменён более новым документом |

Ни дата документа, ни статус `reviewed` не делают его каноном. Канон — только
то, что попало в спеку.

### 2. Разбор

Прочитать документ целиком и сравнить со спеками. Каждое расхождение разобрать:
что это на самом деле.

**Снимать самому** (записать решение в «Снятые противоречия» с пометкой
«агент»):

- одно слово в двух значениях — развести термины в глоссарии;
- смена значения по умолчанию у поля, которое в модели уже есть;
- неполный перечень в одном документе, когда другой его дополняет;
- пункт, на который спека уже ответила раньше.

**Нести владельцу** — только то, где выбор меняет деньги, сроки или обещание
пользователю/клиенту. Список «все расхождения подряд на решение» — это разбор,
переложенный на владельца; так не делать.

Важно: более поздний документ обычно **расширяет** модель, а не отменяет
старые функции. Брать «всё из самого нового» — значит потерять функции,
которые в новом просто не упомянуты.

### 3. Дистилляция в спеку

**Один файл — один домен** (`accounts.md`, `billing.md`, `notifications.md`).
Каждая сущность объявляется **в одном** файле; остальные ссылаются на неё и не
переопределяют.

Шаблон файла спеки:

```markdown
# Accounts: учётные записи и вход

> **Статус: provisional.** Собрано агентом 28.09.2026.
> Источники: docs/incoming/ТЗ на личный кабинет v2.md §§2–4; docs/incoming/Созвон 20.09.md.
> Владелец дельт: <имя>.

Одна-две фразы: что этот домен хранит и за что отвечает.

## Сущности

### User

| Поле | Значение |
|---|---|
| `id` | |
| `email` | уникален, хранится в нижнем регистре |
| `status` | `invited` \| `active` \| `blocked` |

## Правила

1. Заблокированный пользователь не может войти; активные сессии гасятся сразу.
2. ...

## Критерии приёмки

- Вход с неверным паролем 5 раз подряд блокирует вход на 15 минут.
- ...

## Открыто

- Нужен ли вход через Google на первом этапе.
```

Правила формы:

- **Статус** в шапке: `provisional` — предложение агента, не решение. Пункт,
  подтверждённый владельцем, помечается датой и именем: `*(подтвердил Иван 30.09)*`.
- **`Источники:`** в шапке обязательны — откуда взято.
- **`## Открыто`** обязателен и пустым не бывает. Пустой раздел значит, что
  вопросы перестали записывать.
- Там, где решения нет, а без него строить нельзя, — записать требование с
  разумным умолчанием и пометкой `DECISION 2026-09-28` (решение агента,
  действует как provisional, пока владелец не подтвердит или не заменит). В
  «Открыто» — только настоящие развилки.
- **Спека не хранит состояние задач.** Ссылка на задачу — можно (`#12`); слова
  «открыта», «сделано», «в работе» рядом с ней — нельзя: состояние живёт в
  трекере, копия в спеке устаревает.

### 4. Дельта: как менять спеку

Замысел поменялся — правится **сама спека**, второй документ рядом не
заводится.

- Изменённый пункт помечается `*(дельта 28.09)*`.
- Основание (входящий документ или задача) называется в тексте пункта или в
  сообщении коммита.
- Статус входящего документа в индексе обновляется.

Пример:

```markdown
1. Заблокированный пользователь не может войти; активные сессии гасятся в течение
   минуты *(дельта 28.09, ТЗ v2 §3 — было «сразу»)*.
```

Если в шапке накопилось пять-шесть дельт и пришёл документ, меняющий жанр
целиком, — переписать спеку связным текстом «по состоянию на дату», а историю
дельт унести в датированный отчёт в `docs/journal/`.

### 5. `specs/README.md` — карта

```markdown
# Спеки

## Домены

| Спека | Хранит | Ключевые сущности |
|---|---|---|
| glossary.md | термины продукта | — |
| accounts.md | пользователи, вход, роли | User, Session, Role |

## Приоритет источников

| Источник | Отменяет | Основание |
|---|---|---|
| docs/incoming/ТЗ v2.md | в ТЗ v1 — только раздел о тарифах | решение владельца 25.09 |

## Снятые противоречия

| Тема | Формулировки | Принято | Кто решил | Спека |
|---|---|---|---|---|
| «клиент» | покупатель (ТЗ §2) — компания-арендатор (созвон 20.09) | покупатель = Customer, компания = Organization | агент | glossary.md |
```

Дата документа основанием отмены не служит — только явное решение.

### 6. От спеки к коду

- Задача в трекере ссылается на конкретный пункт спеки
  (`specs/accounts.md#правила`, п. 1).
- Готовность задачи проверяется по «Критериям приёмки» спеки; каждый критерий
  — тест или сценарий, который его проверяет.
- Нашёл при реализации, что спека неполна или неверна, — сначала дельта в
  спеке (или вопрос в «Открыто»), потом код. Код не должен тихо отличаться от
  спеки.
- Спека — «как задумано». Если реальность разошлась с замыслом, это находка:
  либо чинить код, либо дельтой менять замысел.

## Вопросы владельцу

Задавать **пакетом в конце хода**, а не по одному. Каждый вопрос — с вариантами
и предложением агента по умолчанию, чтобы владелец мог ответить «да» или одним
словом. Всё, что агент может решить сам (технология, структура кода, имена),
не спрашивать — решить и записать в журнал.

**Старт проекта**

1. Кто владелец продукта — чьё слово окончательное, когда документы расходятся?
2. Какие документы есть? Прислать всё, включая старые версии и переписку.
3. Кто пользователи и какую одну задачу они решают первой?
4. Что входит в первый выпуск, а что точно нет?
5. Есть ли сроки, бюджет, внешние обещания (клиенту, инвестору, на демо)?
6. Ограничения: где будет работать, какие данные, что нельзя (персональные
   данные, платежи, чужие API)?
7. Где трекер задач и как владелец хочет видеть прогресс?

**По ходу разбора** — только то, что меняет деньги, сроки или обещание наружу:

- «Документ A говорит X, документ B — Y. Выбор влияет на <что>. Предлагаю X,
  потому что <одна фраза>. Подтверждаете?»
- «В спеке нет ответа на <что>. Без этого нельзя сделать <что>. Предлагаю
  <умолчание>, записал как `DECISION`. Оставляем?»
- «Этот документ заменяет прежний целиком или дополняет?»

**Не спрашивать владельца**: столкновения терминов, умолчания у существующих
полей, архитектуру и библиотеки, всё, на что спека уже отвечает.

После ответа — сразу дельта в спеке с именем и датой подтверждения, вопрос
убирается из «Открыто».

## Проверки перед коммитом

Агент проверяет сам (можно оформить скриптом):

- каждый файл в `docs/incoming/` есть в `index.yaml`, и каждая запись указывает
  на существующий файл; `sha256` совпадает;
- у записи `distilled` непустой `distilled_into`, и эти спеки существуют;
- у каждой спеки в шапке есть `Статус`, `Источники:`, `Владелец дельт`;
- у каждой спеки есть непустой `## Открыто`;
- сущность из таблицы доменов в `specs/README.md` объявлена ровно в одной спеке;
- рядом со ссылкой на задачу нет слов о её состоянии.

## Коротко для агента

1. Требования — только из `specs/`.
2. Входящий документ не правится и сам канон не меняет.
3. Спека меняется дельтой с датой и основанием.
4. Расхождение сначала разобрать самому; владельцу — только развилки про
   деньги, сроки, обещания.
5. «Открыто» не бывает пустым; состояние задач в спеке не пишется.
6. Код не расходится со спекой молча.
