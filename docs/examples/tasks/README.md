# Задачи GitHub на диске: устройство и образцы

`tools/backlog.py` копирует задачи (issues) из GitHub в папку `docs/tasks/`: по файлу на
задачу. У каждого файла две половины. Верх приходит из GitHub и обновляется при каждой
синхронизации. Низ пишет Claude по ходу работы: что выяснил, что не сработало, с чего
продолжать. Скрипт низ не трогает никогда.

Зачем: между сессиями Claude всё забывает. Низ файла — его память по задаче: новая
сессия открывает файл и продолжает с места, где остановилась прошлая. Искать по
задачам — обычным `grep`, вместе с кодом. Почему устроено так — [../../WHY.md](../../WHY.md).

Правила работы с задачами — раздел «Задачи» в [CLAUDE.md](../../../CLAUDE.md).

## Образцы в этой папке

Это образцы для чтения, а не задачи проекта: `sync` и `grep -ri … docs/tasks/` их не видят.

| Файл | Что показывает |
|---|---|
| [INDEX.md](INDEX.md) | оглавление, его пишет `sync` |
| [g-0012.md](g-0012.md) | задача в работе: верх из GitHub, низ заполнен |
| [g-0009.md](g-0009.md) | закрытая задача с нетронутым пустым низом |
| [draft-zvuk-pryzhka.md](draft-zvuk-pryzhka.md) | черновик новой задачи, ещё не отправлен |

## Команды

```bash
python3 tools/backlog.py sync                 # GitHub → docs/tasks/
python3 tools/backlog.py sync --check         # не писать, показать расхождения
python3 tools/backlog.py review               # обзор: что застряло, где пусто, что недоделано
python3 tools/backlog.py resume 12            # задача №12: состояние и наш низ
python3 tools/backlog.py new docs/tasks/draft-имя.md             # показать черновик
python3 tools/backlog.py new docs/tasks/draft-имя.md --confirm   # завести задачу
python3 tools/backlog.py comment 12 --section "Что установлено"            # показать
python3 tools/backlog.py comment 12 --section "Что установлено" --confirm  # отправить
```

`sync`, `review`, `resume` только читают GitHub и пишут в `docs/tasks/`. `new` и `comment`
пишут в GitHub: без `--confirm` они только показывают текст, с `--confirm` — отправляют.
Скрипту нужны только Python 3.9+ и `gh`, без pip.

## Настройки

Репозиторий скрипт узнаёт у `gh`, префикс имени файла — две буквы из имени репозитория
(`game` → `ga-0012.md`). Чтобы задать своё — `.backlog.json` в корне проекта:

```json
{"prefix": "g", "tasks_dir": "docs/tasks", "project": 3}
```

`project` — номер доски GitHub Projects, если задачи разложены по колонкам
(Todo / In Progress / Done). Тогда колонка появится в поле «Доска». Для доски `gh` нужен
доступ: `gh auth refresh -s read:project` — это делает хозяин.

## Файл задачи

`docs/tasks/g-0012.md` — задача №12, префикс `g`. Номер дополняется нулями до четырёх
цифр, чтобы файлы шли по порядку.

```
# g#12 — Название из GitHub
> строка: когда снят верх
| таблица полей: состояние, доска, метки, исполнитель, даты, ссылка |
## Описание из трекера
## Комментарии из трекера
<!-- ↓↓↓ ниже наше: скрипт эту часть не трогает ↓↓↓ -->
## Чем возобновлять
## Что установлено
## Что опровергнуто
## Тупики
## Ход работы
## Что осталось          ← этот раздел добавляется, когда есть недоделанное
```

Разделитель — строка-метка, ровно такая, посимвольно, только копированием:

```
<!-- ↓↓↓ ниже наше: скрипт эту часть не трогает ↓↓↓ -->
```

Всё выше метки перезаписывается каждым `sync`: правки там пропадут. Всё ниже — не
трогается. Файл без метки скрипт считает целиком нашим и ничего из него не стирает.

Что писать в разделы низа — образец в [g-0012.md](g-0012.md):

| Раздел | Что туда |
|---|---|
| Чем возобновлять | первый шаг для следующей сессии: какой файл открыть, что запустить, что проверить |
| Что установлено | проверенные факты — с файлом и датой |
| Что опровергнуто | «думали X — проверили так-то — оказалось не так» |
| Тупики | куда не ходить и почему |
| Ход работы | короткая хронология: дата — что делали — что вышло |
| Что осталось | недоделанное; `review` собирает эти разделы из всех задач в начало отчёта |

## Новая задача

Черновик `docs/tasks/draft-<короткое-имя>.md`: первая строка `# Название`, строка
`Milestone: <имя>`, если задача входит в milestone, дальше текст задачи (что сделать,
«Готово, когда»), ниже метки — низ (можно пустой). Образец —
[draft-zvuk-pryzhka.md](draft-zvuk-pryzhka.md).

Дальше `new … --confirm`: задача заводится в GitHub, черновик переименовывается в
`g-00NN.md`, низ переносится как был, верх дописывает `sync`. В конце `new` печатает
итог: `заведена: g#13 «Звук прыжка» → milestone Демо`.

Строка `Milestone:` в тело задачи не идёт — в GitHub это отдельное поле. Milestone, которого
в GitHub нет, `new` не заводит, а останавливается и называет существующие: опечатка в
имени не должна молча создать новый. `Milestone: —` или без строки — задача без milestone.

Когда заводить без вопроса, а когда после «да» хозяина — правило 5 в
[CLAUDE.md](../../../CLAUDE.md): просьба хозяина — сразу; то, о чём не просили, — после «да».

## Что скрипт делает сам

- Находит в задачах похожее на пароли и ключи (токены GitHub, ключи `sk-…`, токены
  Telegram-ботов, `password=…`) и тогда ничего не пишет на диск и не отправляет в GitHub.
  Такой ключ надо убрать из задачи и заменить новым: раз он лежал в задаче, его могли
  увидеть.
- Задачи, закрытые как «не будем делать» (`not planned`), на диск не копирует: их текст
  читался бы как задание. В `INDEX.md` строка о них остаётся и ведёт на GitHub.
- Пишет `INDEX.md` (все задачи одной таблицей, с колонкой Milestone) и по команде
  `review` — `REVIEW.md` (обзор).
