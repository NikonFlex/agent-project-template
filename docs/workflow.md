# Рабочий процесс

1. **Инженер фиксирует задачу.** Формулирует наблюдаемый результат и сценарий проверки,
   ссылается на требования, задаёт допустимые файлы и отдельно отмечает открытые вопросы.
2. **Sol пишет короткий план.** В записи задачи остаются результат, требования,
   ограничения, рекомендуемый путь и проверки. Каждый спорный случай получает пример входа и
   ожидаемого результата. Например, при округлении рублей 149 копеек дают 1 рубль,
   а 150 копеек дают 2 рубля.
3. **Neon проверяет сложный план.** Читает затронутые требования и код, ищет пропущенные
   контракты, риски для старых данных и лишние правки. Sol исправляет план.
4. **Flash реализует в отдельном треде на том же worktree.** Читает итоговую запись задачи.
   Сверяет план с кодом, выбирает подходящий способ в рамках требований и кратко объясняет
   существенные отклонения. Прогоняет проверки и сдаёт дифф.
5. **Приёмка.** Закрепите вердикты Jev по требованиям, плану и реализации. Для каждого ID
   приложите относящийся к нему фрагмент диффа и вывод теста. Хеш приёмки берётся из текущего
   коммита и рабочего диффа. Успех варианта Jev v2 требует зелёных тестов, всех этапов с
   `passed` и актуального хеша приёмки. Красный или неоднозначный вердикт сохраняется в отчёте.
6. **Ночью Neon ревьюит изменения приложения.** Скрипт готовит дифф и отчёт проверок.
   Аудитор проверяет код, тесты и спеки и оставляет находки с доказательствами.

Базовый дневной маршрут — Sol и Flash. Neon добавляется на стыках и в ночном ревью.
GLM Idle рассматривается как дополнительный режим для фоновых задач.

## Запуск Рундо

В BB скажите **«реализуй задачу #N через Рундо»** или запустите из треда в корне проекта:

```sh
python3 -m tools.rundo run 42
```

Для Python-задач нужны Python 3.12+, pytest, настроенные в BB Codex и OpenCode, Antigravity для сложных задач и
установленный [bb-jev](plugins.md) с доступом к TypeSafe. Перед первым платным запуском
сверьте модели в `tools/rundo/config.py` с каталогом своих провайдеров. Один штатный прогон
делает три запроса Jev и запускает четыре модельных треда, пять при ревью Gemini.

Рундо читает постановку из файла задачи по `.backlog.json`; `--request-file FILE` задаёт её
явно. Код и тесты живут в одном выделенном worktree от текущего коммита. Дочерние треды
работают в режиме `accept-edits`. Gemini нужен при пяти или более уникальных путях,
новом или неизвестном контракте либо пробеле в спеке. Отдельный тестировщик готовит красный
pytest, реализация проходит тот же тест и `tools/check.sh --quick`. Jev связывает требования,
план и приёмку с фактическим диффом. Отдельный тред записывает черновик в `pr.json`.

Состояние в `tmp/rundo/<номер>/state.json`. Повтор команды продолжает сохранённый прогон.
Квитанции, логи и черновик лежат в `tmp/rundo/<номер>/` выделенного worktree, путь печатает CLI.
Push, публикация PR и выкладка требуют отдельной команды.

Для экранной задачи можно задать адрес локального стенда в `RUNDO_BRAILLE_BASE`,
путь к JSON со списком шагов в `RUNDO_BRAILLE_STEPS` и путь к JSON со значениями
в `RUNDO_BRAILLE_VALUES`. Контроллер собирает наблюдения Braille после зелёных тестов.
Без указанного адреса этот шаг пропускается.

### Рундо с Jevstice

Установите [bb-jevstice](../plugins/bb-jevstice/README.md). Кнопка **Jev** в шапке включает
диагностику для текущего треда и его новых непосредственных детей, включая новые роли Рундо.
Чтобы включить её при запуске Рундо, выполните `python3 -m tools.rundo run 42 --jevstice`.
Дополнительные запросы к судье выполняются по необходимости. Их число и журнал видны через
`bb jevstice status`. Общий счётчик доступен в **Limits → Jev**.

## Ночной аудит

`python3 tools/nightly_audit.py --base HEAD` запускает сбор отчёта. `tools/nightly_automation.py`
запускает его при свежих коммитах в каталоге приложения `src`, тестах, спеках или конфигах приложения. В новом
проекте расписание BB добавляется отдельно.

Дополнительные настройки в `pyproject.toml`:

```toml
[tool.agent_project.nightly]
crap_threshold = 30
mutation_targets = ["src/my_package/example.py"]
mutation_workers = 2
hypothesis_profile = "deep"
```

Укажите `hypothesis_profile` после регистрации такого профиля в проекте. Проверка мутаций
запускается при изменении файла из списка. Для раскладки `src` тесты импортируют пакет по его имени и добавляют `src` в pythonpath. Import Linter запускается при наличии его
конфигурации. Для метрик и мутаций установите `tools/nightly-requirements.txt`.
