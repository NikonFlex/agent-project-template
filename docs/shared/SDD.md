# Разработка от требований (SDD)

Процесс, в котором продукт пишут агенты под управлением инженера, а требования — проверяемая
цепочка от документа заказчика до работающей системы. Что нужно агенту до первого действия —
`AGENTS.md`; формат спеки, старшинство источников, глоссарий, решения инженера и вопросы
продакту — [openspec/README.md](../../openspec/README.md). Где шаг выполняется руками, а не
программой, — таблица «Что выполняется руками» в конце.

## Роли

| Роль | За что отвечает | Что пишет |
|---|---|---|
| Продакт (заказчик) | замысел продукта и наблюдаемый результат | PRD для новой области; ΔP для работающей; ответы на вопросы |
| Инженер (хозяин репозитория) | путь от замысла до работающего продукта | спеки, онтологию, задачи, сценарии проверки, статус требований |
| Агенты-исполнители | код и тесты по задаче | код, тесты, записи в файле задачи |
| Агент-приёмщик | проверка задач на рабочем контуре (`/accept`) | запись проверки, закрытие или возврат задачи |

Спека — артефакт инженера: продакт её читает и ссылается на требования, но не согласует.
Неопределённость, которая задевает пользовательский сценарий, бизнес-логику, права,
сущности, необратимое действие или критерий приёмки, — вопрос продакту. Продакт не
управляет разработкой посреди итерации: идея по ходу задачи идёт в следующий ΔP.

## Этапы

| № | Этап | Что делается | Чем подтверждается |
|---|---|---|---|
| 1 | Продакт готовит PRD или ΔP | новая область — документом; работающая — пунктами ΔP с адресами требований | пункт ΔP называет существующее требование |
| 2 | Инженер готовит спеку | онтология, требования со строкой источника, сверка в обе стороны, задача на требование, сценарий до кода | приборы сверки; сценарий красный до кода |
| 3 | Агенты пишут код | исполнитель получает задачу с требованиями и готовый сценарий | гейты CI |
| 4 | Инженер доводит до рабочего контура | слияние, выкладка пайплайном, прогон сценариев на контуре | запись прогона |
| 5 | Продакт проверяет на контуре | ему отдаётся путь, у которого все обязательные требования проверены | число проверенных требований пути и дата |
| 6 | Продакт пишет ΔP | решение — в журнал, изменение — пунктом ΔP | строка журнала с типом и адресом |

Дальше цикл: проверка продактом → журнал решений → ΔP → правка спеки → код → рабочий контур →
проверка продактом. Механические проверки — обязательная часть: изменение, которое их не
прошло, не сделано и продакту не передаётся. Контуров три: локальный стенд, рабочий контур
(dev) и прод; «сделано» значит «работает на проде», пока прод заморожен — «проверено на dev».

## Суть

Требования приходят от продакта документами: ТЗ, PRD, списки правок, ответы на вопросы.
Они противоречат друг другу, устаревают и пишутся в разных жанрах. Поэтому:

| Каталог | Что там | Правило |
|---|---|---|
| `docs/incoming/` | присланные документы как получены | не правятся; это **не требования** |
| `openspec/specs/` | требования: каталог на сущность или экран | единственный источник требований |
| `openspec/README.md` | старшинство источников, глоссарий, решения, вопросы | правит инженер |

Код пишется **только по `openspec/specs/`**. Нашёл требование только во входящем
документе — это не требование, а повод записать его в спеку (или спросить продакта).
Каталог входящих исключён из обычного поиска (`.rgignore`); искать там явно:
`rg --no-ignore <слово> docs/incoming/`.

## Конвейер

```
документ пришёл → снимок в incoming + запись в индекс + строка в «Источники и старшинство»
               → сверка с онтологией: нет ли уже такой сущности, роли, пути
               → требование со строкой источника (или решение инженера, или вопрос продакту)
               → задача со ссылкой на требование → код → проверка по сценарию требования
```

### 1. Приём документа

- Файл кладётся в `docs/incoming/` **как получен**, в Markdown (Google Doc, PDF, DOCX —
  конвертировать в `.md`, текст не менять). Номера строк файла — адреса в строках источника.
- Файл больше не правится никогда. Пришла новая редакция — новый файл, старая запись
  получает статус `superseded`.
- Запись в `docs/incoming/index.yaml`:

```yaml
- path: docs/incoming/ТЗ на личный кабинет v2.md
  received: '2026-09-28'
  origin: письмо от заказчика; адрес оригинала, если документ выгружен по ссылке
  sha256: <sha256sum файла>
```

- Строка в таблице «Источники и старшинство» `openspec/README.md`: номер старшинства и как
  источник называется в ссылках («ТЗ», «PRD»). Более поздний документ — меньший номер.
- Разметка: каждый код, пункт или блок источника — строка покрытия в
  `openspec/source-map.md`: за какой спекой записан либо «не вошло: причина».

Ни дата документа, ни приём не делают его каноном. Канон — только то, что записано
требованием.

### 2. Разбор

Прочитать документ целиком и сравнить со спеками и онтологией: не вводит ли он вторую
сущность, роль или кабинет там, где такая уже объявлена; второй путь для задачи, которая уже
решается; переход, которого нет в таблице; поведение, противоречащее существующему
требованию. Нашлось — требование не записывается, продакту уходит вопрос с адресом
существующего требования.

**Снимать самому** — строкой в «Снятые противоречия»: столкновение терминов (развести в
глоссарии), смена значения по умолчанию у существующего параметра, неполный перечень в одном
из документов, пункт, на который спека уже ответила.

**Нести продакту** — только то, где выбор меняет пользовательский сценарий, бизнес-логику,
права, сущности, необратимое действие или критерий приёмки.

Более поздний документ обычно **расширяет** модель, а не отменяет старые функции. Брать «всё
из самого нового» — значит потерять функции, которые в новом просто не упомянуты.

### 3. Сверка с источником в обе стороны

- **Прямая, требование → источник.** Каждое требование называет строки источника, из которых
  взято. Поле, число, состояние и текст в кавычках есть на названной строке.
- **Обратная, источник → требование.** Каждая непустая строка источника названа требованием,
  картой или записана в `openspec/reverse-ledger.md` с классом: служебное, покрыто, вне
  объёма. Строка с поведением, данными, правами, текстом или ограничением в реестр не идёт —
  она становится требованием.

Обратная сверка повторяется после каждого нового источника и после правки, задевшей больше
одной спеки. Существование строк и связей проверяет `tools/source_check.py`; совпадение
смысла требования с текстом строки — инженер.

### 4. Требование

Формат и шаблоны — `openspec/README.md`, правила текста — `docs/agents/specs.md`. Коротко:

- Каталог на спеку: сущность или экран. Сущность объявлена в одной спеке.
- Требование — одно поведение с MUST, строкой `**Источник:**` и сценарием GIVEN/WHEN/THEN
  с конкретными значениями из источника.
- Где источник молчит, а без решения строить нельзя, — требование с источником
  «решение агента <дата> — <что решено>» и строка в «Решения инженера».

### 5. Изменение требования и ΔP

На работающую область продакт присылает не новый PRD, а **ΔP** — документ с пунктами (формат
и порядок — [Журнал решений и ΔP](product/Журнал%20решений%20и%20ΔP.md)). ΔP принимается как
источник (шаг 1), каждый пункт — строка журнала, спека правится в тот же день.

Замысел поменялся — правится **само требование**: текст, сценарий и строка источника,
которая теперь называет новый документ или ответ продакта. Истории в спеке нет: «было» и
причина — в коммите и в задаче, по которой меняли. Правка, которая меняет заголовок
требования, добавляет или удаляет требование, правит и всё, что ссылается на адрес, в том
же PR.

### 6. Пользовательские пути

Путь — шаги одной роли со ссылками на требования: `openspec/paths/<роль>-<NN>-<слово>.md`,
формат и правила — [openspec/paths/README.md](../../openspec/paths/README.md). Каждое требование
названо в пути или в `openspec/paths/not-in-paths.md` с классом. Продакту отдаётся путь, у
которого все обязательные требования проверены.

### 7. От спеки к коду

- Задача называет требования, которые закрывает: `` `openspec/specs/<спека>/spec.md` —
  «<заголовок>» `` (`docs/agents/tasks.md`). До нарезки релиза на задачи и после неё
  `tools/task_links.py` печатает требования без задачи и задачи без требований; каждое
  требование из первого перечня получает задачу.
- Готовность проверяется сценариями требований; каждый сценарий — тест или исполняемая
  проверка.
- Нашёл при реализации, что спека неполна или неверна, — сначала правка требования (или
  вопрос продакту), потом код. Код не должен тихо отличаться от спеки.

### 8. Сценарий до кода, проверка на контуре, статус

- **Сценарий проверки** пишется по тексту требования до кода, сессией, которая код этой задачи
  не пишет; первый прогон красный по причине из требования. Формат, режимы, контрольный
  сценарий, квитанция — [tests/scenarios/README.md](../../tests/scenarios/README.md).
- **Требование закрывает проверка на рабочем контуре** после выкладки. Зелёный CI и
  прочитанный код требование не закрывают.

| Способ | Что это | Даёт статус |
|---|---|---|
| испытание | исполняемый сценарий на контуре; запись с коммитом, контуром, временем и итогом | ✅ |
| демонстрация | проход руками или скриптом по API; запросы и ответы в файле задачи | ✅ |
| анализ | замер по базе или журналу, только чтение — для требований о данных и числах | ✅ |
| осмотр | чтение кода, тест в репозитории | 🚚, если сделано; 🟡 или ❌, если нашёл, чего нет |

- Результат проверки — свидетельство: ответ сервера, строка базы, запись прогона. Пересказ по
  памяти проверкой не считается. Не прошла — требование открыто, задача возвращается
  исполнителю со свидетельством в теле, путь продакту не отдаётся.
- Статус каждого требования — `docs/shared/product/Таблица требований.md`; перенос из
  записей прогона — `python3 tools/req_status.py --write`. Продакту отдаётся путь, у которого
  все требования с MUST проверены: путь, число проверенных требований и дата замера.

## Обратная связь

Каналов четыре; в шаблоне — описание, программы собираются под проект.

- **Таблица обратной связи.** Продакты и тестеры пишут баги и предложения в общую таблицу;
  мост раз в час превращает новую строку в задачу с меткой `triage` и сразу вписывает номер
  задачи в строку (по одной строке, не пачкой), заводит карточку на доске, обновляет колонку
  «ход работы» по стадиям (создана, назначена, проанализирована, на проде, сделано), переносит
  ответ продакта комментарием, а задачи с меткой `needs decision` дописывает в лист с вопросом.
  Колонки ищутся по заголовкам, а не по буквам; строка с номером второй раз не переносится;
  пустые поля строку не отвергают. Стадию «проанализирована» мост видит по тексту в задаче
  сверх его собственного — поэтому разбор уходит в саму задачу, а не только в файл на диске.
- **Чат команды.** Бот принимает текст задачи, готовит заголовок и тело, показывает черновик и
  создаёт задачу по кнопке; ключ «чат + номер сообщения» не даёт создать вторую при повторной
  доставке. Задачи приходят тремя путями (мост, бот, люди) — дубли ищутся по копии на диске,
  дубль закрывается причиной `duplicate` со строкой об оставшейся задаче.
- **ΔP** — документ продакта с пунктами по требованиям (см. журнал решений).
- **Описание продукта для продактов** — папка, собранная из `openspec/`: документы по
  областям, оглавление с адресами требований, пути по ролям, глоссарий с решениями и
  вопросами, таблица требований; в первой строке — дата сборки и коммит; требование с
  источником «решение агента» помечено «решение разработки». Сборка отказывает, если спека
  не отнесена к области. Продакт подключает папку своему ИИ-помощнику и по ней пишет ΔP.
- **Макеты.** Нормой служит текст. Макет новой страницы — зрительная цель, требования пишутся
  текстом, результат сверяется снимком экрана. Макет существующей страницы — перечень
  «добавлено, убрано, изменено», который инженер заносит пунктами ΔP. Элемент, которого нет в
  тексте, требованием не становится; макет расходится с текстом — действует текст, вопрос.

## Выкладка и контуры

В шаблоне — описание; пайплайн собирается под стек проекта (`/bootstrap`).

- Образ собирается один раз и продвигается по digest. Выкладка на dev сама проверяет, что
  коммит в `main` и полный прогон зелёный.
- Перед подъёмом контейнера — цепочка, каждое звено которой останавливает выкладку: та ли
  база, проверка окружения, резервная копия базы, миграции.
- После подъёма — `/health` отдаёт коммит образа: без этого упавший на старте контейнер
  засчитывался за успешную выкладку. Красная выкладка — сообщение в чат; автоотката нет.
- Прод — ручной запуск человеком с digest, который уже побывал на dev; откат называется до
  выкладки. Через границу слоёв первым выкладывается поставщик (обратносовместимо), вторым
  потребитель; откат — в обратном порядке.
- Постоянное состояние серверов — роли Ansible; руками меняется только временное, с откатом.
- Зелёный прогон не значит работающий сервис: после выкладки факт снимается с системы —
  запрос, журнал контейнера, экран.

## Выпуск версии

Номер версии и `CHANGELOG.md` собираются из заголовков коммитов (Conventional Commits,
`docs/agents/tasks.md`) — руками не пишутся. Инструмент — git-cliff, настройки — `cliff.toml`.

- Выпускает человек: Actions → `release` → Run workflow (`.github/workflows/release.yml`).
  Агент запускает его только по «да» на конкретный выпуск. Что выйдет — заранее:
  `python3 tools/changelog.py`.
- Номер — semver от последней метки `vX.Y.Z`: `fix`, `perf` и прочие — патч, `feat` —
  минорная цифра, `!` или `BREAKING CHANGE` — старшая; до `1.0.0` несовместимое поднимает
  минорную. Первый выпуск — `v0.1.0`.
- В CHANGELOG — заголовки по разделам (несовместимое, новое, исправлено…). Учёт
  (`chore(backlog)`), выпуски, слияния и коммиты без типа не идут; подвал «Implements …» не
  печатается.
- Выпуск — коммит `chore(release): vX.Y.Z` в `main`, метка и GitHub Release с теми же
  строками. Нет коммитов с типом с прошлой метки — выпуск отказывает.

## Метрики

| Метрика | Откуда |
|---|---|
| доля требований релиза, проверенных на рабочем контуре, по областям, с датой | таблица требований (`tools/req_status.py`) |
| доля пунктов ΔP типов PRD mismatch (потеря между источником и требованием) и Bug (между требованием и кодом) | журнал решений, столбец «Тип» |
| доля задач, закрытых записью прогона без человека | трекер |
| время от вопроса продакту до ответа | «Вопросы продакту» |
| FPSR — доля задач с первого промпта, PR на задачу | `tools/fpsr.py`, `/fpsr` |

Число пунктов ΔP после первой сборки показывает качество постановки: если большая часть —
«имели в виду другое», потеря произошла до кода.

## Вопросы продакту

Порядок — `openspec/README.md`, таблица «Вопросы продакту». Сначала поиск по источникам:
вопрос, ответ на который там есть, вопросом не является. Вопрос — с вариантами и тем, что
сделано до ответа: работа ответа не ждёт, «сделано до ответа» — решение инженера со своей
строкой. Решение до ответа не вводит сущность, роль, кабинет или путь и не делает
необратимого с данными.

**Старт проекта** — спросить продакта: какие документы есть (прислать всё, включая старые
версии и переписку); кто пользователи и какую задачу они решают первой; что входит в первый
релиз; сроки и внешние обещания; ограничения (данные, платежи, чужие API).

**Не спрашивать продакта**: столкновения терминов, умолчания у существующих полей,
архитектуру и библиотеки, всё, на что спека уже отвечает.

## Проверки

`tools/check.sh` запускает:

- `openspec validate --specs --strict` — форма: `## Purpose` от 50 знаков, MUST в
  требовании, `#### Scenario:` у каждого требования, требование до 500 знаков;
- `tools/spec_check.py` — входящие в индексе с тем же `sha256`; тип спеки в Purpose и его
  разделы; строка источника у каждого требования; заголовки не повторяются; сущность
  объявлена в одной спеке; связь называет объявленную сущность; нет истории и состояния
  задач; нет оценок в THEN;
- `tools/source_check.py` — ссылки на строки источников (по виду ссылки), решения агента ↔
  таблица «Решения инженера», перечень спек в карте, пункт карты упомянут в своей спеке,
  каждая непустая строка источника названа ссылкой, картой или реестром;
- `tools/paths_check.py` — форма путей, названные требования существуют, каждое требование
  в пути или в `not-in-paths.md`;
- `tools/task_links.py` — ссылки задач на требования существуют; сведения: требования без
  задачи, открытые задачи без требований;
- `tools/scenario.py --selftest` и `--control` — раннер сценариев краснеет на испорченном
  ожидании и на контрольном сценарии; `tools/req_status.py` — каждое требование в таблице
  один раз, статус из списка, сводка сходится.

## Что выполняется руками

| Что | Как сейчас | Что задумано |
|---|---|---|
| совпадение смысла требования с текстом строки источника | сверяет инженер | прибора нет |
| сверка нового требования с онтологией (вторая сущность, второй путь) | сверяет инженер | прибор на слово, употреблённое как сущность |
| журнал решений продакта | ведёт инженер со слов продакта | — |
| прогон сценариев на рабочем контуре после выкладки | `scenario.py run --contour dev --record-run` вручную, перенос — `req_status.py --write` | прогон после каждой выкладки без модели и раз в сутки с моделью |
| закрытие задачи | руками, сводкой из пяти пунктов | запись прогона закрывает задачу, красный прогон переоткрывает |
| правка ожиданий существующего сценария | обычный PR | такой PR сам не сливается и ждёт человека |
| статус требований по пути | считается руками | матрица «требование → сценарий → последний прогон» |
| мост таблицы обратной связи, бот, сборка описания продукта | нет в шаблоне | собрать под проект |

## Коротко для агента

1. Требования — только из `openspec/specs/`.
2. Входящий документ не правится и сам канон не меняет.
3. У требования есть строка источника; источник молчит — решение агента со строкой в таблице.
4. Расхождение сначала разобрать самому; продакту — только то, что меняет поведение.
5. Код не расходится со спекой молча.
