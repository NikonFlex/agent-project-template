# Журнал решений и ΔP

Решения продакта и пункты изменений (ΔP). Ведёт инженер со слов продакта; порядок —
`docs/shared/SDD.md`, «Изменение требования и ΔP». Значимые технические выборы — не здесь, а
в `docs/decisions.md`.

## Формат ΔP

Документ продакта с пунктами. Первая строка — версия описания продукта, по которой он написан
(«Сборка: <дата>, <коммит>»), либо «описание продукта не использовалось».

| Поле | Что в нём |
|---|---|
| Тип | Bug — работает не так, как в требовании; PRD mismatch — требование записано не так, как в источнике; UX issue — работает по требованию, но неудобно; Improvement — изменить требование; New requirement — требования ещё нет |
| Требование | адрес `<спека>: <заголовок>`; для нового — спека и соседнее требование |
| Было | текст требования или увиденное; для бага — шаги, учётная запись, адрес страницы, снимок экрана |
| Стало | что видит и что может пользователь, с числами и текстами дословно |
| Сохранить | что из работающего не должно измениться |
| Приоритет | P0, P1, P2 либо «не определён» |

## Обработка

1. Документ принимается как источник: файл в `docs/incoming/`, строка в «Источники и
   старшинство» `openspec/README.md`.
2. Каждый пункт — строка журнала ниже: тип, адрес, приоритет; приоритет — в поле задачи.
3. Пункт без адреса или с несуществующим адресом — продакту в тот же день, с двумя-тремя
   ближайшими требованиями на выбор.
4. Требование изменилось после сборки, по которой написан ΔP, — продакту с текущим текстом.
5. Спека правится в тот же день; строка источника требования называет пункт ΔP. Решения
   инженера и вопросы, которые пункт снимает, уходят из таблиц `openspec/README.md`.
6. Изменённое требование получает задачу; сценарий правится раньше кода. Требования из
   «Сохранить» — их сценарии входят в проверку задачи.
7. У пунктов Bug и PRD mismatch называется звено, где потеряно: источник → требование,
   требование → задача, задача → код, код → проверка.

Мелкие баги продакт пишет в таблицу обратной связи, называя требование; ΔP присылает
документом.
