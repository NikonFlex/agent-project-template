# Сценарии проверки

Сценарий — исполняемая проверка поведения на поднятой системе: шаги через API и ожидания.
Каталог на сценарий: `tests/scenarios/<имя>/scenario.json`. Раннер — `tools/scenario.py`.

```json
{
  "name": "bundle-prose-instead-of-json",
  "зачем": "Модель вернула прозу вместо объявленного JSON. Проверяется, что отказ назван.",
  "требования": ["drafts: Отказ при ответе не по схеме"],
  "steps": [
    {"kind": "http", "method": "POST", "path": "/auth/login",
     "body": {"email": "{admin_email}", "password": "{admin_password}"},
     "expect_status": 200, "extract": {"token": "$.access_token"}},
    {"kind": "stub", "scenario": "provider", "state": "bundle_not_json"},
    {"kind": "http", "method": "POST", "path": "/drafts",
     "headers": {"Authorization": "Bearer {token}"},
     "body": {"prompt": "Техника безопасности на складе"},
     "expect_status": 201, "extract": {"draft_id": "$.draft_id"}},
    {"kind": "wait", "db": "main", "query": "select status from drafts where id='{draft_id}'",
     "until": ["completed", "failed"], "timeout_s": 600, "poll_s": 5}
  ],
  "expect": [
    {"kind": "sql", "name": "ни один отказ не приехал безымянным", "db": "main",
     "query": "select count(*) from jobs where status='failed' and coalesce(failure_rule,'')=''",
     "expect": 0},
    {"kind": "no_provider_egress", "name": "ни одного обращения мимо стаба", "expect": "ok"}
  ]
}
```

`требования` — адреса `<спека>: <заголовок>`, которые сценарий проверяет; по ним
`tools/req_status.py` переносит итог прогона в таблицу требований.

## Виды

Перечни объявлены в раннере один раз (`STEPS`, `EXPECTS`); незнакомый вид — отказ до запуска.

| Шаг | Что делает | Нужно от `stand.json` |
|---|---|---|
| `http` | запрос, ожидаемый код, `extract` — значения в переменные, `save` — имя ответа | `base_url` |
| `wait` | опрос базы до одного из `until` с таймаутом | `db` |
| `container` | `action` (restart, stop, start) над `service` | `compose` |
| `stub` | переключить состояние подставного провайдера | `stub_url` |

| Ожидание | Что сличает |
|---|---|
| `sql` | значение запроса к базе |
| `field` | поле ответа (`response` — имя из `save`, по умолчанию последний) |
| `no_field` | поля в ответе нет |
| `log` | строка есть в журнале контейнера |
| `stub_log` | строка есть в журнале подставного провайдера |
| `no_provider_egress` | обращений к настоящему провайдеру не было |
| `const` | константа — только для контрольного сценария |

`{имя}` в строках — переменная: из окружения (учётные данные — в `.env`, не в сценарии) или
извлечённая шагом. Незаданная переменная останавливает прогон.

## Стенд

Как обращаться к системе — `tests/scenarios/stand.json` (образец — `stand.example.json`,
заполняет `/bootstrap` под стек): адрес API, команда к базе (`{query}` подставляется),
compose-проект, адрес подставного провайдера. Шаг, которому нужен неописанный кусок стенда, —
отказ до запуска. Локальный стенд — вся система одним compose-проектом: база, Redis, бэкенд,
фронтенд, подставные провайдеры; порты нестандартные, сеть своя.

## Режимы обращений к модели

| Режим | Что делает | Когда |
|---|---|---|
| `replay` | подставной провайдер отвечает записанными ответами (кассета) | по умолчанию; без ключа и расхода |
| `record` | запросы идут к настоящему провайдеру, ответы записываются | после правки промпта или формы вызова |
| `live` | настоящий провайдер без записи | приёмка перед push |

Раннер требует `--mode` и передаёт его стенду в `SCENARIO_MODE`; незаявленное значение —
отказ. Кассета сличается с запросом и перестаёт подходить после правки промпта: красный
кассетный сценарий после такой правки — повод перезаписать кассету, а не чинить продукт и
не ослаблять ожидания. Отдельный каталог заготовок — внесение отказов: провайдер отвечает
прозой вместо JSON, обрывает ответ, отказывает один раз.

## Правила

- Сценарий пишется по тексту требования **раньше кода**, сессией, которая код этой задачи не
  пишет, и сначала прогоняется. Причина: агент способен написать код и тесты, которые
  подтверждают его собственное неверное прочтение требования.
- Для поведения, которого ещё нет, первый прогон обязан быть красным по причине, названной в
  требовании.
- Для поведения, которое уже работает, первый прогон зелёный. Тогда сценарий прогоняется ещё
  раз с испорченным ожидаемым значением или заведомо плохим входом и обязан покраснеть;
  запись этого прогона — в задаче.
- Исполнитель получает сценарий как данность. Сценарий расходится с требованием — правится
  требование или сценарий отдельной правкой, а не в работе над кодом.
- Значения сценария — из источника требования.
- Сценарий повторяем: свои учётные записи с меткой прогона, чистка перед прогоном.
- Контрольный сценарий [control/](control/scenario.json) с заведомо невыполнимым ожиданием
  считается без поднятой системы; `python3 tools/scenario.py --control` в `tools/check.sh`
  обязан увидеть его красным.
- Проверки экранов — скрипты на playwright (Chromium без окна): вход своей учётной записью,
  проход по страницам, снимок экрана, сверка текста и состояний.

## Прогон, запись, квитанция

```
python3 tools/scenario.py run --mode replay                        # все сценарии, локально
python3 tools/scenario.py run <имя> --mode live                    # один, перед push
python3 tools/scenario.py run --mode live --contour dev --record-run   # на контуре, с записью
```

- Запись прогона — `openspec/runs/<время>-<контур>.json`: коммит, контур, время, итог по
  сценарию, требования, первое несбывшееся ожидание. Перенос в таблицу требований —
  `python3 tools/req_status.py --write`; запись с локального стенда статус не меняет.
- Последняя строка отчёта — квитанция: хеш дерева кода, режим, исход. Хеш считается по файлам
  git, кроме неисполняемого (`tools/receipt.json`, «exclude»): правка только тестов или
  документов квитанцию не сбрасывает, откат к дереву с квитанцией её сохраняет. Квитанция
  дописывается в `receipts.jsonl` каталога состояния стенда (`STAND_STATE_DIR`, по
  умолчанию `~/.local/state/stand`) — вне репозитория; её читает сторож push.
